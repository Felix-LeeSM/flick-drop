# Live Relay Architecture and Security

Live Transfer (`/api/pipe/*`, `internal/piperelay`) streams an age-encrypted payload from one browser to another through API memory, hopping from the sender's API replica to the receiver's (`service-topology.md`). It writes nothing to PostgreSQL or object storage, and its waiting-room metadata lives in non-persistent Valkey.

## Coordinator and Valkey Rendezvous (`internal/piperelay`)

- `internal/piperelay/coordinator.go` implements `Coordinator` and its public methods (`Init`, `Join`, `Status`, `Wait`, `Select`, `Decline`, `Leave`, `Cancel`, `ActiveSessions`, `Drain`, `Close`).
- `internal/piperelay/room.go` stores rendezvous state in Valkey: one hash per session, `{Namespace}room:{roomID}` (fields `rev` and `state`, JSON of `room`), where `roomID` is the hex HMAC-SHA-256 of the 6-digit code under `CoordinatorOptions.KeySalt` (`FLICK_RATELIMIT_KEY_SALT`). Every write is a compare-and-set (`casRoomScript`) that publishes on `{Namespace}ev:{roomID}` in the same Lua call; `Coordinator.update` re-reads and retries a lost race.
- Each API process holds one Pub/Sub pattern subscription (`{Namespace}ev:*`) and fans it out to local waiters through `roomHub` (`internal/piperelay/room.go`). A waiter registers before reading the room and re-reads at least every `resyncInterval` (2 seconds), so a lost Pub/Sub message only delays wake-up.
- `Coordinator.settle` (`internal/piperelay/room.go`) applies end rules on every read: the 3-minute window closing ends a room with `ErrExpired`; a chosen connection that has not opened `Receive` within `CoordinatorOptions.PresenceTimeout` (`defaultPresenceTimeout`, 35 seconds) ends it with `ErrSessionClosed`; a streaming room ends only past `MaxTransferDuration` (`defaultMaxTransferDuration`, 10 minutes). `Coordinator.cleanOnce` runs the same rules every `CleanInterval` (30 seconds) on every replica.
- Bounded concurrency: `{Namespace}rooms` (a sorted set scored by each room's deadline) caps live sessions across replicas at `FLICK_PIPE_MAX_CONCURRENT` (default 100) in `createRoomScript`.
- `Coordinator.Drain` makes open `Status` and `Wait` calls answer immediately; `cmd/flick-api/main.go` calls it on `SIGTERM` before the 50-second `shutdownTimeout`, so waiting browsers re-poll through another replica.
- `Coordinator.Close` leaves rooms in Valkey untouched (other replicas keep serving them) and stops every goroutine the coordinator started.
- A Valkey error surfaces as `ErrUnavailable` (`internal/httpapi/piperelay.go:writePipeError` answers `503 service_unavailable`). The loops waiting for the other side (`Receive` before the stream arrives and `waitForReceiver` inside `Send`) treat a failed read as transient and re-read at the next `resyncInterval` until the window closes, because the shared Valkey client (`internal/httpapi/ratelimit.go`) never retries and times out after 250 ms (`TestStream_SenderSurvivesOneFailedReadWhileWaiting`, `TestStream_ReceiverSurvivesOneFailedReadWhileWaiting`).

## Pod-to-Pod Stream Path (`internal/piperelay/stream.go`)

- `Receive` registers a local `streamSlot`, writes the connection as attached and `CoordinatorOptions.AdvertiseIP` (`FLICK_POD_IP`, `127.0.0.1` outside Kubernetes) into the room, then waits for the stream.
- `Send` claims the sender side once (`room.SenderClaimed`; a second `Send` returns `ErrAlreadyConnected`), so every later failure inside `Send` ends the session (`causeClosed`) instead of leaving the receiver waiting. It waits for the receiver (`waitForReceiver`), draws a one-time stream secret, writes only its SHA-256 and the stream start into the room, and POSTs the body to `http://{room.ReceiverIP}:{CoordinatorOptions.InternalPort}` + `StreamPathPrefix` + `roomID` with `InternalTokenHeader` and `StreamSecretHeader`. The kind and encrypted filename travel only as headers on that request.
- `Coordinator.serveStream` (mounted by `cmd/flick-api/main.go` on `FLICK_INTERNAL_HTTP_PORT`, kept inside `internal/piperelay` because it is relay transport rather than a public API endpoint) requires `FLICK_INTERNAL_TOKEN`, a valid room ID, a waiting local slot, a streaming room, and the matching secret, then copies the body into an `io.Pipe` read by the receiver's response through a pooled, cleared 64 KiB buffer (`copyWithPool`). It answers `200` only after the receiver finishes reading.
- `Send` (`Coordinator.stream`) returns the sender body's read error on failure (`502 transfer_failed`), `ErrExpired` past `MaxTransferDuration` (`410`), and `io.ErrClosedPipe` for any answer other than `200` (`502 receiver_disconnected`).
- The stream client dials only an IP literal parsed with `netip.ParseAddr` on the configured internal port, never follows redirects (`http.ErrUseLastResponse`), and never uses an HTTP proxy (`newStreamTransport`), so a tampered room cannot aim it at another host or port. In Kubernetes, `deploy/base/api.yaml` `NetworkPolicy/flick-api` admits only other `flick-api` pods to `FLICK_INTERNAL_HTTP_PORT`.
- The hop is plain HTTP inside the cluster network; the bytes on it are the same age ciphertext the browsers exchange.

## End-to-End Encryption and What Valkey Holds

The stream is end-to-end encrypted against a passive server:

- The receiving browser generates a fresh hybrid ML-KEM-768 + X25519 age identity for each receive attempt (`web/src/lib/crypto/pipe.ts:createPipeReceiverKey`, built on `web/src/lib/crypto/age.ts:generateSecretIdentity`). The identity stays in that attempt's browser memory only (`web/src/lib/components/ReceiveCodeModal.svelte:joinAndReceive`): no browser storage, no URL, no request, no log.
- `POST /api/pipe/join` carries only its public recipient as `{"recipient":"age1pq1..."}`. `internal/httpapi/piperelay.go:joinPipe` validates it (`validPipeRecipient`: prefix `age1pq1`, lowercase bech32 characters, at most `pipeRecipientMaxChars` 4,096 characters, canonical ML-KEM-768 + X25519 parse; otherwise `400 invalid_recipient`) and stores it on that connection in the Valkey room.
- `GET /api/pipe/wait` hands recipients to the sender token holder only: each waiting row carries its recipient, and once `status` is `ready` the top-level `recipient` names the attached receiver's. Neither `/join`, `/status`, nor `/receive` returns a recipient to any receiver.
- The sender encrypts the stream and filename to that recipient with age (`web/src/lib/state/pipe-relay.svelte.ts:streamPayload`, using `encryptToRecipient` and `encryptPipeFilename`); the receiver decrypts with its identity (`decryptWith`, `decryptPipeFilename`).
- The server issues no key material for a code transfer: no salt, no passphrase, and the 6-digit code only routes requests. A curious or passive server, its logs, a dump of its memory, or a dump of Valkey therefore hold recipients and (memory only) ciphertext but nothing that decrypts the stream. A code transfer takes no passphrase on either side; the link tab's passphrase never reaches it.

**Valkey data boundary:** Valkey runs with `--save "" --appendonly no`, so nothing reaches disk. Each room hash is keyed by the HMAC-SHA-256 of the 6-digit code under `FLICK_RATELIMIT_KEY_SALT` (preventing bare SHA-256 brute-forcing of 900,000 codes). Its JSON state holds the SHA-256 of the sender token, each connection's ID, verification number, coarse device label, public age recipient, HMAC'd client key and network, the decline block list (HMAC'd client keys), the receiver replica's IP, the SHA-256 of the one-time stream secret, and timestamps. It never holds ciphertext, the encrypted filename, the 6-digit code, the sender token, the stream secret, or a raw client hash: `internal/piperelay/stream_test.go:TestStream_ValkeyHoldsNoCiphertextCodeOrToken` dumps every key mid-stream and checks the values for the ciphertext, the encrypted filename, the sender token, and the raw client hashes, and the key names for the code. The stream secret exists only inside `Send` and its outgoing request, so Valkey holds no more than the SHA-256 that `Send` writes. A room expires one minute after its own deadline (the 3-minute window, or `maxTransferDuration` once streaming), and an ended room stays one minute as a tombstone so devices still waiting learn how it ended. Anyone who can read Valkey can read the connection IDs and recipients of live rooms, so a deployment keeps Valkey reachable from the API replicas only: `deploy/base/valkey.yaml` `NetworkPolicy/valkey` admits `flick-api` pods alone, and the pod has no volume.

**Known limit (active server):** The key exchange is not authenticated against an actively malicious server, which could swap in its own recipient on `/wait`, decrypt, and re-encrypt to the real receiver. The 3-digit confirmation number does not detect this: the server draws it, and it is not derived from either key. Defending against an active server would require out-of-band recipient verification, which is not implemented.

## Credentials, Waiting-Room Confirmation, and Presence Leases

- `POST /api/pipe/init` returns the 6-digit code and a random sender token. Only the sender token unlocks `/wait`, `/select`, `/decline`, `/cancel`, and `/send`; a wrong token answers `404` like an unknown code (no code oracle). With the right token, `/select` and `/decline` answer `409 not_pending` for a connection that already left or never existed. `Cancel` on an ended session answers `ErrNotFound` (`404`) like a wrong token (`internal/piperelay/coordinator.go` `Coordinator.Cancel`).
- `POST /api/pipe/join` is the only call that accepts a bare 6-digit code. It is rate-limited by `FLICK_OPEN_RATE_PER_MIN` per client network (IPv6 collapsed to `/64`, `internal/httpapi/ratelimit.go:clientNetwork`; `/api/pipe/join` and `/api/v1/pipe/join` share one bucket) and returns an unguessable `crypto/rand` connection ID required by `/status` and `/receive`.
- Every live relay session is a waiting room holding up to `MaxPendingConnections` (10) pending connections, at most `MaxPendingPerNetwork` (3) per client network (next gets `409 network_full`), each with its own `crypto/rand` 3-digit verification number unique among waiting connections and independent of the 6-digit code.
- The receiver reads its 3-digit number to the sender over another channel (voice, chat); the sender sees every waiting connection with its number, a coarse device label such as "Safari on iPhone", and its wait time, then selects the matching row (`Select`). Every other waiting connection ends with `ErrNotSelected` ("The sender chose another device") and receives nothing.
- The check is the sender's eyes: there is no receiver-side typing or mutual confirmation, and it proves only that the stream goes to the device that showed that number. It does not defend against a compromised server, which draws the numbers and could swap the recipient (the active-server known limit above).
- A waiting receiver long-polls `Coordinator.Status` (up to 25 seconds per poll so proxies such as Cloudflare with a 100-second idle cut never see silence) and calls `Receive` only once selected (`Receive` while still waiting returns `409 awaiting_decision`).
- A waiting connection counts as present while `{Namespace}poll:{roomID}:{SHA-256 of connection ID}` exists: `Join` creates it, and each `Status` call refreshes its `PresenceTimeout` (35 s) TTL when it starts and ends (`acquireLeaseScript`, `releaseLeaseScript`). `Coordinator.pruneIdle` drops expired leases, freeing the slot without a decline or burn.
- **Leave:** a waiting receiver that closes the dialog, starts over, or hides the page calls `POST /api/pipe/leave` with its code and connection ID (`web/src/lib/components/ReceiveCodeModal.svelte:leaveWaitingRoom`, a `keepalive` fetch so it outlives a closing tab). `Coordinator.Leave` removes that waiting connection and bumps the room version, so the sender's `Wait` drops the row at once instead of after `PresenceTimeout`. It blocks nothing (the device may join again) and answers `ErrNotPending` for a connection already settled, chosen, or gone. A receiver that loses its network without leaving still drops only after `PresenceTimeout`.
- One connection holds at most `MaxStatusPollsPerConnection` (2) open `Status` calls (`409 poll_in_progress`), tracked in `{Namespace}polls:{roomID}:{SHA-256 of connection ID}` scored by hold + `PresenceTimeout` so a killed replica's stale polls stop counting (`TestCoordinator_DeadReplicaPollStopsCounting`). `/status` is also rate-limited to 120 calls/min per client network (`internal/httpapi/piperelay.go:pipeStatusRatePerMinute`), so a connection ID cannot pile up server goroutines and sockets.
- **Decline:** `Decline` ends that connection (`ErrDeclined`, "The sender declined this device"), reopens its slot, and keeps the session alive. It blocks the same client key (HMAC under `FLICK_RATELIMIT_KEY_SALT` of SHA-256(client network + User-Agent), with the client network resolved like the rate limiter's, `internal/httpapi/piperelay.go:pipeJoinClient`) for the session's lifetime. The block is deliberately coarse: another device behind the same NAT or IPv6 /64 with the same browser and OS string is blocked too for that one short session, and a determined person can change network or User-Agent to get back in; the sender can deny them again.
- The declined browser also records a SHA-256 of code + `sessionExpiresAt` (computed once when `/join` answered) in `sessionStorage` (`web/src/lib/state/pipe-declined.ts`), so a reload does not ask again and the memory lapses with that session. The entry never holds the code itself or any key, and a 6-digit code's hash is brute-forceable, so it is treated as no more secret than the code the user already typed on that device.
- **No burn on rejected receivers:** A wrong 6-digit code never reaches a session (the code is the lookup key), so a per-session failed-attempt counter could only ever count people who held the right code. Late, extra, declined, idle, room-full (`409 room_full`, the 11th waiting device), or network-full receivers therefore never end or count against a session; online code guessing is bounded only by the `/join` rate limit (per client network) and the 3-minute window. `/join` and `/select` return `410 expired` once the window closed, even before cleanup removes the session.
- **Started streams are never cut by a burn:** `Cancel` returns `409 streaming` once bytes flow, and `settle` skips streaming rooms until `MaxTransferDuration` (10 minutes). `Cancel`, TTL settlement, and `Send` marking stream start all use CAS on the Valkey room, so a cancel racing a starting stream either ends the session before any byte flows or loses with `409 streaming` (`TestCoordinator_CancelRacingSendNeverCutsAStream`). Only the stream itself failing, either side disconnecting, or a replica still streaming when `cmd/flick-api/main.go:shutdownTimeout` (50 s) ends cuts it.
- **Residual risks:** A holder of the right 6-digit code can keep slots for the session's 3-minute window, up to `MaxPendingPerNetwork` per network, by polling `/status` or by re-joining roughly every 35 s as each idle connection drops (spending only `/join` rate-limit tokens). Filling all 10 slots takes at least 4 networks, and the sender sees every such row and can `Decline` it, but a code holder with many networks can still crowd the room until the sender asks for a new code. An IPv6 `/56` (256 `/64`s) or `/48` (65,536) holder gets that many join buckets and per-network caps. A global or per-session cap on joins is a possible future hardening; it is not implemented. A replica killed without `SIGTERM` leaves its open `Status` polls counted for up to 25 + 35 s, potentially causing `ErrPollInProgress` for that connection until expiry.
- The API never logs 6-digit codes, verification numbers, room IDs, sender tokens, connection IDs, client keys, recipients, or User-Agents. Device labels live in the session's Valkey room only, for the session's lifetime plus the one-minute tombstone.
